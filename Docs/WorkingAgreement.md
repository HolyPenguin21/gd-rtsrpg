# Fantasy RTS/RPG — Working Agreement

> Правила менеджера и агентов. Действуют на ранних стадиях разработки; изменения согласовывает владелец.

## Роли

**Владелец:** утверждает ключевые решения, изменения архитектуры, визуальные результаты и приёмку этапов.

**Менеджер/архитектор:** аудит, границы модулей, GitHub Issues, ревью PR снизу вверх, решение о готовности к слиянию.

**Агент-исполнитель:** перед работой изучает реальные исходники и документацию; реализует только текущий Issue и создаёт PR с честным отчётом о проверках.

## Перед каждым Issue

1. Проверить актуальный `main`, открытые PR, реально существующие файлы и модули.
2. Прочитать `Docs/GDD.md`, `Docs/Decisions.md`, **`Docs/Architecture.md`** и соответствующий этап `Docs/ImplementationPlan.md`.
3. Проверить, нет ли модуля с нужной ответственностью; не создавать параллельную реализацию.
4. Сформировать минимальный объём, требования к данным, зависимостям, демонстрации и приёмке.
5. Неутверждённые параметры не объявлять официальными: временный локальный выбор допустим лишь при необходимости и с явной пометкой.

## Реализация

- Отдельная ветка и PR к `main`; слияние только после приёмки.
- Изменения ограничены текущим Issue, включая необходимые связанные сцены, настройки и документацию.
- Сохранять Unity `.meta`/GUID; не удалять или менять их без необходимости.
- Не создавать универсальные managers, registries, service locators, инфраструктуру или пустые каталоги на вырост.
- Один источник истины для геометрии террейна, маршрута, движения, приказов и боевых расчётов.
- **Не реализовывать следующий Stage** в рамках текущего PR.
- **Не использовать Unity NavMesh**. ECS, Jobs/Burst и сложные зависимости требуют отдельного решения владельца.
- Не проводить массовую очистку Unity пакетов без обоснования, включая `manifest.json` и lock-файл.

## Проверка качества

Проверять **снизу вверх**: данные и сериализация → компоненты и скрипты → сцены, .meta и ссылки ассетов → пользовательское действие → смежные системы. Проверять взаимные зависимости и ошибочные предположения.

На текущем этапе **не писать Unit Tests, Integration Tests, PlayMode Tests, test fixtures, тестовую инфраструктуру, тестовый CI/benchmark**. Это принятое временное решение; к тестам возвращаемся только после отдельного одобрения.

Если Unity доступна:
1. Открыть проектную сцену и проверить импорт пакетов.
2. Проверить компиляцию C# после изменений.
3. Запустить Play Mode и выполнить короткий smoke check именно новой функции.
4. Проверить видимые граничные случаи.

Если Unity недоступна, пометить каждый соответствующий пункт **NOT RUN** и описать причины и то, что удалось проверить статически. Отсутствие ошибок в старом Editor.log не заменяет запуск.

## Формат PR

- **Summary:** игровой результат.
- **Scope:** затронутые файлы и системы.
- **Architecture:** фактические границы, зависимости, корректировки Architecture.md.
- **Verification:** проведённые проверки, результаты и NOT RUN.
- **Out of scope:** что сознательно не реализовано.
- **Risks / Open questions:** риски и необходимые решения.

## Приёмка

Менеджер сопоставляет PR с Issue и контрактами, проверяет не только локальный diff, но и связи с соседними модулями. Ошибки данных или противоречия утверждённым решениям требуют доработки. После приёмки — merge в `main`, обновление статуса и подготовка следующего Issue.

## Изменение архитектуры

Если задача требует менять границы системы, агент **до кодирования** готовит краткое предложение: проблема → минимальное изменение → владельцы данных/зависимости → риски. Сначала согласование и обновление Architecture.md, затем реализация.
