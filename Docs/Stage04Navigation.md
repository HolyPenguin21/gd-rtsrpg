## Использование и владение

На существующем Terrain GameObject в SampleScene добавлены `TerrainNavigation` и отключаемый `NavigationDemo`. Builder остаётся единственным создателем Surface/mesh. Navigation читает именно `builder.Surface`, не asset-параметры, Mesh, цвет, декоративный шум, Physics или NavMesh. Входные TerrainMapData не изменяются.

`TerrainNavigation.Grid` — снимок поверхности и фактической матрицы Transform. Разрешены смещение, yaw, одинаковый положительный XZ scale и независимый положительный Y scale. Наклон, shear, reflection, нечисловая матрица, переполнение world coordinates или >262144 подъячеек дают понятную ошибку. Числа/лимиты — локальная конфигурация Stage 04, не утверждённые игровые стандарты.

Builder сообщает `SurfaceChanged` при снятии старой и публикации новой поверхности. TerrainNavigation снимает/retire старый Grid; ошибки Builder оставляют Grid отсутствующим. Новая карта не сохраняет handles/занятость старой. Transform сравнивается в LateUpdate; при реальном изменении навснимок пересоздаётся один раз. Если будущий потребитель меняет transform и сразу запрашивает путь в том же кадре, он должен явно вызвать `Rebuild()` перед запросом. Stage 05 должен зарегистрировать существующие статические постройки заново после нового снимка.

## Координаты и запросы

- Один блок = 4×4 клетки существующего Surface. `Vector2Int.y` означает Z, а не мировую высоту.
- `NavigationPose.Cell` — нижняя XZ клетка занятого прямоугольника. `Facing` — N/E/S/W; 1×2 занимает 1 по X, 2 по Z в N/S, 2 по X, 1 по Z в E/W. Для квадратов facing не меняет геометрию, в выходном пути он канонизирован в North.
- `NavigationFootprint(1,1)`, `(1,2)`, `(2,2)` — поддерживаемые размеры. Другие размеры явно отклоняются.
- `NavigationRequest(start, goal, footprint, maxExpanded=20000, allowPartial=false)` задаёт оба footprint целиком и конечную ориентацию.
- `new NavigationPathfinder(grid).Find(request)` — явный синхронный запрос. Никаких поисков в Update/таймера repath нет.
- `NavigationPoint` содержит pose и world Vector3 **центра прямоугольника**, включая Y логической верхней поверхности. Есть `Grid.Point`, `WorldPoint(cellX,cellZ)` и `TryWorldToCell(world,out cell)`. Последний математически преобразует XZ, не делает terrain/cursor picking и не проверяет присланную высоту world Y.
- `WorldPoint` интерполирует углы Cell в double, затем применяет LocalToWorld. В точности на границе выбирается клетка +X/+Z (у внешнего края последняя внутренняя); для валидного footprint внутренние профили непрерывны. Не использовать произвольный sample через скальную стену как разрешение перейти её.

Короткий пример интеграции:

```csharp
var grid = terrainNavigation.Grid;
var request = new NavigationRequest(
    new NavigationPose(new Vector2Int(5, 1), TerrainDirection.North),
    new NavigationPose(new Vector2Int(5, 9), TerrainDirection.North),
    new NavigationFootprint(1, 2));
var path = new NavigationPathfinder(grid).Find(request);
if (path.IsCurrent && path.Status == NavigationStatus.Success)
{
    // Stage 05 may consume path.Points. Stage 04 performs no movement.
}
```

Перед созданием Pathfinder проверять `Grid != null`. Отсутствующая поверхность/ошибка построения — `TerrainNavigation.Error`; ошибки конфигурации Grid/Group — ArgumentException. Невозможный пользовательский путь возвращает статус, не бросает исключение.

## Статусы результатов

| Статус | Значение |
|---|---|
| Success | Достигнут точный goal и ориентация прямоугольника; квадратная ориентация геометрически эквивалентна |
| Partial | Только при allowPartial; безопасный префикс до ближайшего по эвристике раскрытого состояния; **не** разрешение считать goal достигнутым |
| NoPath | Очередь исчерпана либо группа не нашла свободное достижимое место в своём radius |
| InvalidRequest | Неверный footprint, enum или бюджет |
| InvalidStart | Старт выходит за карту, занят или пересекает уступ внутри footprint |
| InvalidGoal | Непроходимый/занятый/внешний goal; автоматически «подталкивать» одиночную цель нельзя |
| BudgetExceeded | Ограничение раскрытий/кандидатов; нужен отдельный повторный запрос, отсутствие пути не доказано |
| Stale | Запрос к retired Grid |

Path хранит `Status`, `Reason`, `Points`, `Cost`, `Expanded`, `Revision` и живой `IsCurrent`. После изменения blockers Status исторического результата не переписывается, **IsCurrent становится false**. Групповой результат также имеет IsCurrent. Потребитель обязан проверять валидность до исполнения.

## Переходы и footprint

1. Восемь направлений; стоимость axial=10, diagonal=14, quarter-turn=10. Octile heuristic игнорирует повороты, остаётся допустимой/согласованной. Heap tie-break: F, принадлежность corridor, H, Z, X, facing. Нет случайного порядка Dictionary/HashSet в расширении состояния.
2. Для каждой занятой клетки проверяются occupancy и **все внутренние ортогональные границы** footprint по `TerrainSurface.IsBoundaryBlocked`. Эта функция сравнивает оба конца edge profile в целых четвертях уровня. Совпадение только одного угла не открывает проход. Поэтому смена уровня возможна только через реальный непрерывный ramp contract N/E/S/W.
3. При translation проверяется весь прямоугольник swept bounds. Диагональ включает оба ортогональных промежуточных положения и их границы; 1×2/2×2 не могут задеть угол строения или пересечь скалу краем. Проверка консервативна, но в прямом коридоре шириной footprint сохраняет точные размеры.
4. Поворот 1×2 — отдельный переход ±90° при неизменном lower-left anchor. Центр смещается на полклетки по X/Z. Проверяется bounding box объединения описанных окружностей обоих центров: он покрывает весь вращаемый прямоугольник и линейный сдвиг центра. Требуется **свободная 4×4 площадка** вокруг anchor, без внутренних cliff edges. Это консервативное ограничение: в некоторых тесных местах физически возможный поворот будет отклонён. Протискивания или мгновенного поворота через стенку нет. 180° = два quarter-turn.
5. Facing не привязан принудительно к вектору translation: вытянутый footprint может двигаться боком, занимая соответствующую ширину. В узкой полосе проходит только ориентация вдоль неё; A* может предварительно развернуться на свободной площадке.
6. Точки не сглаживаются/не сокращаются. Stage 05 обязан интерполировать XZ в допустимом transition, брать текущий Y из WorldPoint, учитывать смену размера/центра при turn и не соединять удалённые точки прямой через стену.

## Статические блокеры и пересчёт

`grid.TryAddBlocker(RectInt cells, out handle, out error)` / `RemoveBlocker(handle)` регистрируют только прямоугольную статическую занятость. При наложениях используются счётчики: снятие одного blocker не снимает другой. Сборка игрового здания/ограничение стройки плоской площадкой не входят в API; демонстрационный blocker разрешено поставить и на рампу.

Обновляются лишь cells прямоугольника, revision увеличивается и посылается Changed. Все старые path/group результаты недействительны. Нет списка активных Transform или исполнения маршрутов. Повторный Find/Plan — минимальная точка интеграции для явного repath Stage 05; demo отдельно предлагает кнопку Replan. Retire идемпотентен, запрос к старому Grid возвращает Stale, удаление чужого/неизвестного handle возвращает false. Handle имеет смысл только вместе с исходным Grid.

## Группы, сложность и бюджеты

`NavigationGroupPlanner.Plan(members,target,radius=12,totalExpanded=80000,localExpanded=8000,candidatesPerMember=32)`:

1. Один общий A* для 1×1 guide от первого участника к точке. При успехе строится corridor ±2 клетки от spine. Guide не обещает проходимость для крупных footprint.
2. Кандидаты целей идут расширяющимися Chebyshev-кольцами от target, в стабильном порядке Z/X. Сначала размещаются крупные footprint; результаты сохраняют исходные индексы участников.
3. Для каждого кандидата проверяются полный footprint, доступные orientation и отсутствие наложений с ранее назначенными **конечными** местами. Затем локальный A* в corridor. При необходимости разрешён unrestricted fallback тем же solver, за оставшийся бюджет участника/группы. Коридор не может принудить пройти через скалу.
4. Резервируется только успешная конечная площадь; промежуточные пути могут пересекаться. Это не live occupancy и не симуляция одновременного движения. Для группы у края/узкой рампы допустим неполный результат с явным статусом каждого участника.

Жёсткие пределы: 100 участников, radius≤32, ≤128 кандидатов на участника, общий cap≤1000000 раскрытий. По умолчанию участник тратит **суммарно не более 8000** раскрытий на все corridor/fallback/candidate запросы; вся группа вместе с guide — ≤80000. Никакого неограниченного полного поиска для каждого участника/каждого Update.

Sparse A* хранит только обнаруженные состояния; ≤4 orientation на клетку. Стоимость запроса O((B+1) log(B+1)), память O(B+1) при expansion cap B и ограниченной степени графа. Кандидаты ≤(2r+1)², occupancy ≤4 cells на pose. Группа ограничена суммой B, плюс O(N·r²) проверок кандидатов и сортировка O(N log N). В худшем случае без corridor пользы solver всё равно выполняет несколько индивидуальных поисков, но cap контролирует совокупную стоимость. При исчерпании cap возвращается отказ, не скрытая очередь или продолжение в кадрах. Числа требуют будущего профилирования, производительность в Unity не заявлена проверенной.
