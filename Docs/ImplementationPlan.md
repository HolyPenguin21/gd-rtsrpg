# Fantasy RTS/RPG — Implementation Plan

> Дорожная карта по стадиям, а не календарный план. Редакция 03.11.2026. Указание следующего этапа **не разрешает** агенту реализовывать его раньше времени.

## Процесс

1. Менеджер изучает актуальные исходники, GDD, Decisions и Architecture.
2. Оформляет ограниченный GitHub Issue: пользовательский результат, ответственность, зависимости, исключения и приёмка.
3. Агент реализует задачу в отдельной ветке и создаёт PR.
4. Менеджер проверяет снизу вверх: данные → классы → сцены и ссылки → пользовательский сценарий → смежные системы.
5. После приёмки PR сливается в `main`, фактическая архитектура фиксируется, ставится следующая задача.

## Stage 01 — принят и объединён

Issue: https://github.com/HolyPenguin21/gd-rtsrpg/issues/2

В исходниках реализованы `RtsCameraController`, `CursorWorldProjection`, карта Camera в существующем Input Actions, интеграция с SampleScene и минимальная плоскость/маркер. Документация фактической архитектуры обновлена. PR #3 объединён в `main`, commit `a09007cb2d697c949d7725a1dc700d358342a0e0`. Статическая проверка проведена; Unity import, C# / shader compilation и все Play Mode smoke checks — **NOT RUN**, редактор отсутствует. Детали: [Stage01Camera.md](Stage01Camera.md).

**Цель:** можно перемещать и масштабировать ортографическую RTS-камеру, а игровая логика получает корректную точку курсора в мировых координатах для будущих команд.

Перед реализацией изучить `SampleScene`, Camera, `InputSystem_Actions.inputactions`, Input System 1.19.0 и контракт координат XZ/Y. Не создавать второй параллельный input framework.

**Объём:**

1. Камера ортографическая и под настраиваемым фиксированным углом к плоскости земли.
2. Панорамирование в XZ, правильно ориентированное относительно камеры.
3. Плавный zoom, настраиваемые границы и устойчивость при достижении пределов.
4. Настройки в Inspector: скорость и плавность передвижения/зума, угол и границы допустимой зоны.
5. Преобразование указателя в точку на опорной плоскости XZ заданной высоты; корректный ответ при отсутствии пересечения. Не разрабатывать контракт Terrain Builder раньше Stage 02.
6. Input через существующий Unity Input System. Раскладка и edge-scroll должны быть явным решением Issue, не превращать стандартные Player actions в якобы утверждённую RTS-схему.
7. Минимальная наглядная сцена; без постоянного игрового мира и других игровых систем.

**Приёмка:** orthographic-проекция, управляемое панорамирование и плавный ограниченный zoom, правильная мировая точка курсора, редактирование настроек без правки кода, отсутствие залипания ввода, целостные ссылки сцены. Выполнить Unity compile/Play Mode/manual smoke там, где возможно, иначе отметить NOT RUN. Обновить таблицу фактических модулей в Architecture.md.

**Не входит:** выделение, unit movement, A*, terrain mesh, procedural maps, combat, RPG, automated tests, ECS/Burst и инфраструктура «на будущее».

## Проверка

На раннем этапе не создавать автоматические Unit/Integration/PlayMode tests, fixtures или специальную test/benchmark инфраструктуру. При наличии Unity — ручное открытие сцены, компиляция и Play Mode; при отсутствии — отчёт NOT RUN. Решение об автоматических тестах принимается владельцем отдельно.
